## What each test was actually for

- **Software** covers the three shapes that behave differently: a tool with a
  contract and a notice deadline (Gong), a self-serve monthly one with no
  contract at all (Loom), and one that forces the "is this one row or several"
  call (Salesforce, three add-ons that cannot be cancelled separately).
- **Process Library** covers three of the five types, each with its own body
  template, and the `Software` relation from a Technical Reference to Gong.
- **Memos** covers three of the seven types, each with a different body
  template, and the `Artifacts` relation into the Process Library.
- **Projects** covers a project built from a Problem Statement memo, which is
  the relation the design leans on, and one with no memo behind it.
- **Tasks** covers three tasks ordered under one project.
- **Calendar** covers an event and a social post deliberately side by side,
  because that is the open question about whether `calendar:new` is one skill
  or two.

## Verified by running

- Every write landed. No select value was rejected, checked against the live
  option lists before writing rather than from the schema documents.
- Six relation types set and returned on read-back: Process to Software, Memos
  to Process, Projects to Memos, Tasks to Projects, Calendar to Projects,
  Calendar to Process.
- `slop-check` over all 17 descriptions and bodies: hard rules clean, no em
  dashes, no short-sentence runs, no artefacts.

## Findings

1. **Two antithesis constructions**, the "the point is not X, it is Y" shape,
   in the task note and the social post. A tic, and worth a rule in the plugin
   because it will recur in every body a skill writes.
2. **No row has an owner**, and `slop-check`'s spec half flags exactly that.
   This is the spec working as written: person fields are never guessed. In
   real use `new` asks. Open question is whether a row with four empty person
   fields is acceptable output.
3. **The calendar asymmetry is now visible in data.** The conference row uses
   `Format`, `Our role`, `Location` and `Link`. The social post uses `Channel`
   and none of those four. One row type fills a different half of the schema
   from the other.

## Needs Sarah

1. Read the rows and say whether the writing passes.
2. `calendar:new`: one skill or two.
3. Is a row with no owner acceptable, or should `new` refuse to finish without
   one.

# Round 2, schema rebuild after Sarah's review

All six databases changed. Old test rows are now stale against the new schema
and get deleted before the next build.

## Applied

**Everywhere**
- `Status` is now the real status property, not a select. All six.
- `Audience` replaced with: Sales, Marketing, Finance, Account Management,
  Partnerships, Ops, Engineering, Product, Design.

**Process Library**
- Dropped `Supersedes`, `Superseded By`, `Verified by`, `Verified date`,
  `Review cadence`.
- `Parent` is now `Parent strategy`. `Last checked for accuracy` is now
  `Last verified`, and it is the only freshness field left.
- `Type` values numbered: 1 - Strategy Decision, 2 - SOP/ROE, 3 - Enablement,
  4 - Reporting, 5 - Technical Reference.

**Software**
- Dropped `Annual cost`, `Renews`, `Given to new teammates`, `Customer facing`,
  `Owner`.
- `Contract dates` is now `Current contract dates`. `Billing owner` is now
  `Accountable owner`, alongside `Technical owner`.
- Added `Plan type`: Monthly, Annual, Multi-year committed, Free.
- Added `Cost band`: Under $1k, $1k to $5k, $5k to $25k, $25k to $100k,
  Over $100k.
- `SOC 2` is a checkbox. Unknown reads as no.
- `Importance` values are now consequence-based: Work stops without it, Work
  gets slower, Convenience.

**Projects**
- RACI: `Owner` became `Accountable`, `Stakeholders` became `Consulted`, and
  `Responsible` and `Informed` were added.
- Added `First task date` and `Last task date`, rollups of the task due dates.
- Added `Task dates`, a formula joining those two.
- Added `Percent complete`, a rollup over task status. **Unverified.**

**Tasks**
- Dropped `Sub-tasks` and `Parent task`. Project and task only. `Order` kept.

**Calendar**
- Dropped `Domain`, `L2C Lifecycle`, `Segment`.

## Two limits, both tested

1. **Page layout cannot be set from the API.** The surface is schema DDL plus
   view configuration. Views control filters, sorts, grouping and which columns
   show in what order. The row page layout, property grouping, the tabs and the
   pop-out sidebar, is not in either. UI only.
2. **Status options cannot be set from the API.** `ALTER COLUMN "Status" SET
   STATUS` works. `STATUS('Draft':yellow, ...)` returns a 400 parse error, so
   the type converts but carries Notion's defaults: Not started, In progress,
   Done. Every custom list is gone and has to be renamed by hand once per
   database.

## Needs Sarah

1. The status option lists, above. Four of the six had meaningful values.
2. `Percent complete` returns from the API without the aggregation recorded,
   unlike the two date rollups which report theirs. Proving it needs real tasks.

# Round 3, the webinar loop end to end

18 new rows. Stale rows from round 1 left in place, not deleted.

## The loop

Strategy decision, "Webinars are the top-of-funnel motion we invest in"
  |- SOP: Webinar registration form setup      -> HubSpot, Goldcast
  |- SOP: Webinar run of show                  -> Goldcast, Zoom
  |- Technical Reference: Registration data flow into the CRM
                                               -> HubSpot, Goldcast, Salesforce

Project, "Q4 webinar, the first on the fixed format"
  |- 8 tasks, ordered, two Done, one In progress
  |- Artifacts -> all four process docs
  |- Calendar -> 3 rows

Calendar
  |- Q4 webinar, live          -> project, run of show, registration SOP
  |- Reminder email, day before -> project
  |- Follow-up, split by attendance -> project, technical reference

Software: Goldcast, HubSpot, Zoom. Page bodies say what is known and name the
source for every field still empty, rather than inventing values.

## Review passes

**slop-check:** hard rules clean. One soft tell, rule-of-three, 5 occurrences.

**Executive feedback contract**, applied in its own order. Four findings, all
real:

1. **The strategy decision has no numbers.** It argues from structure alone and
   its Sources section admits the evidence is missing. For a decision aimed at
   leadership that is the weakest part of the loop.
2. **The registration SOP references a status value that no longer exists.**
   Step 1 says the Calendar row must be `Confirmed`. Converting Calendar to the
   status property replaced that list with Not started / In progress / Done, so
   the instruction cannot be followed.
3. **The calendar is incomplete against the plan.** The strategy and the project
   both specify three promotion emails. The Calendar holds the reminder and the
   follow-up but not the three promo sends, so the task says to add them and the
   calendar does not show them.
4. **Unchecked SOC 2 reads as a failure.** Making it a checkbox means an
   unverified vendor is indistinguishable from one that failed. Goldcast is
   unchecked here because nobody looked, not because the answer is no.

## Cannot verify

`First task date`, `Last task date`, `Task dates` and `Percent complete` return
as opaque references from the API, and the schema lists all four as not
queryable in SQL. **Their values cannot be read through the API at all.** They
have to be checked by eye in the Notion UI.
