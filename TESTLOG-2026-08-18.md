## Findings

   real use `new` asks. Open question is whether a row with four empty person

3. **The calendar asymmetry is now visible in data.** The conference row uses
   `Format`, `Our role`, `Location` and `Link`. The social post uses `Channel`
   and none of those four. One row type fills a different half of the schema
   from the other.

# Correction, added 2026-08-18 after the review rounds

**Round 7 recorded a true observation and drew a false conclusion from it.**

The line "Tasks stays a status property" is accurate about the test workspace.
Tasks was a status property there, and it was still one after the other five
flipped back to select, which is what Round 7 checked and reported.

**What is wrong is the attribution.** That state was made by hand in the UI
during Round 2, where the entry above says "`Status` is now the real status
property, not a select. All six." The installer did not produce it and could not
have. `schema.js` has always created the Tasks `Status` as a select like the
other five, there is no `status` type in `DDL_TYPE` at all, and both DDL forms
for making one were measured on 2026-08-18 to return a 400 at the parser. So the
test workspace stopped being a record of what an install produces the moment the
conversion was done by hand, and Round 7 read the surviving hand-made property as
evidence about the installer.

**What it cost.** `POST-INSTALL.md` and `DECISIONS.md` both went on to tell users
that Tasks ships as a status property and needs no conversion. Anyone following
that would have skipped the one conversion `Percent complete` depends on, and the
rollup would have stayed blank with nothing in the documents to explain it. Found
by review on 2026-08-18, in the same session the error was written. Both
documents are corrected and Tasks is now the sixth row of the conversion table.

**The earlier entries are left as they were written**, in the same way the
Process Library entries were, because they record what was true at the time. This
correction is appended rather than folded into them: a test log edited to match
the code afterwards stops being a record of what happened.

**The general lesson.** A workspace that has been fixed by hand can no longer
answer a question about what the installer does. Every hand fix during testing
has to be written down as a hand fix, or the workspace quietly becomes the wrong
instrument.

# Round 9, measuring against the live workspace to answer the review

Read-only. Nothing was created, changed or deleted in the workspace, so there was
nothing to clean up afterwards.

## The description question, which the repository could not answer

The review said the description round-trip check was skipping a real failure by
testing `'description' in got`, on the reasoning that a real fetch always carries
the field. Nothing in the repository supported that: not one of the 115
properties in `full-install-as-notion-returned-it.json` carries a `description`
key, so from inside the repository the guard looked correct and the reviewer
looked wrong.

**Fetched the live Projects and Software data sources. Every property carries
`description`, and it is the empty string where there is none.** No exceptions
across either database. So the reviewer was right and the fixture is an
incomplete transcription. The guard is removed and the fixture now says in its
own `_comment` what it does not carry.

**This is the second time a fixture has been mistaken for a measurement.** The
first was Tasks, above. A transcription that drops a field looks exactly like an
API that does not return one.

## The row proof was resting on titles

`expectedRows` selected the title property, and `verify` joined the two row sets
with `' | '` and compared the strings. Titles are not unique in Notion and one
containing that separator would collide with a pair of other rows.

**Changed to select `url`, and measured on Calendar / Upcoming:**

- The rule as SQL, `SELECT url FROM <ds> WHERE "Status" = 'Confirmed'`, returned
  three rows.
- The view queried in view mode returned the same three.
- **They come back in two different url shapes.** SQL gives
  `https://app.notion.com/<id>` and the view gives `https://app.notion.com/p/<id>`.
  Comparing what arrives, as the old code did with titles, would have reported
  all three rows as different. Both are reduced to the bare id before comparing,
  and that reduction is now tested against these exact strings.

## The filter shapes, confirmed against a current workspace

The new structural check was built from the fixture. All five live filters match
what it expects: one clause comes back as the top group itself, one `IN` clause
comes back with the top group set to `or`, and two clauses come back as one
sub-group each. `groupBy` comes back as `{property, propertyType}` plus
`hideEmptyGroups` and a sort, which are not checked.

## Found while measuring, and not fixed

**`Projects` in the live workspace has no `Problem Statement` property**, and the
SQL rule for `Projects / Needs attention` fails against it with "no such column".
The manifest still defines relation 5, `projects.Problem Statement` to
`memos.Resulting Projects`, and every schema and skills document still describes
it. The handoff for this work records a decision to drop it, taken during the
Round 2 review, and that decision reached the live workspace by hand and reached
no file here.

So the code and the documents agree with each other and disagree with the
workspace, which is the reverse of the Tasks error and the same underlying cause.
**Answered the same day.** Sarah confirmed the intent: Projects relates to Memos
through the one `Memos` relation, and a project's problem statement is a memo
attached through it. Relation 5 is removed, the remaining twelve are renumbered,
and `Projects / Needs attention` now filters on `Memos` being empty. That view is
deliberately wider than the rule, because a filter that reads the memo `Type`
through the relation would be a rollup filter, and those were measured on
2026-08-17 to be accepted and then silently discarded. Recorded in `DECISIONS.md`.

The fixture is not re-recorded, so it still carries both sides of the dropped
relation and the old view filter. Those three differences are now named one by one
in `full-install.test.js` rather than absorbed into a count, so a fourth
difference fails the test.
